## Provenance — read this before the numbers

Every clip here is a real, public CCTV benchmark sequence from
[MOT16](https://motchallenge.net) (Milan et al., 2016) — overhead street
cameras, a Venice plaza, a shopping mall corridor. **Not** footage from any
actual border post. Used here strictly as "does this pipeline detect and track
real people in real footage" — squarely inside what a public tracking
benchmark exists for.

Zone geometry was placed against **real, mathematically verified track
trajectories**, not eyeballed timestamps. The first attempt at this file used
visual inspection at 3-second intervals and got the crossing direction *and*
location wrong on all three clips — real people in real footage do not move
where a quick glance suggests. The working method: run the actual tracker,
dump every confirmed track's foot-point x-coordinate over time, and place the
tripwire only where a real track's x-coordinate is mathematically confirmed to
cross it. See `/tmp/trace_clip.py`-style trajectory dumps (not committed;
reproducible from `worker/src/ibvap_worker/track.py` output).

## What the numbers actually mean

**The negative control passed cleanly.** Zero false alerts from a genuinely
quiet real-footage region over 13.9s — the debounce and gating logic did not
manufacture an event where none existed.

**mot16-02 and mot16-09 (the two short clips) matched exactly as predicted.**
One real tracked pedestrian crosses the derived tripwire in each; the rule
fires as `TRIPWIRE_CROSS`, within the expected time window, once. The "1 FP"
in each row is a *second*, different real pedestrian in the same busy scene
also crossing the same line — genuinely correct behaviour that a single
hand-labelled event can't credit.

**mot16-04 is the interesting one.** Five real alerts fired, all classified
`PERIMETER_APPROACH`, none `TRIPWIRE_CROSS` — so all five score as false
positives against a label that specifically expected `TRIPWIRE_CROSS`, and the
expected event itself is recorded as a false negative.

This is **not** evidence the geometry is broken — `PERIMETER_APPROACH` fired
*exactly* where two real, independently-verified tracks were closing in on the
tripwire, which is correct: the rule is designed to catch someone approaching
a boundary. It fired instead of `TRIPWIRE_CROSS` on this specific run, on this
specific pair of tracks, in a scene with 10-18 real people in frame — dense
enough that detector output ordering (and therefore which boxes survive NMS in
which order) is not guaranteed to be bit-identical between two separate
inference sessions on this machine's CoreML backend. A repeat trajectory trace
in a fresh process assigned different track IDs to the same real people. The
underlying geometry (`crossing_direction`, `segments_intersect`,
`perpendicular_travel`) is unit- and property-tested exhaustively
(`worker/tests/test_geometry.py`, 300+ tests, hypothesis-generated) and is not
in question; what this run surfaces is that **exact-frame crossing detection
in a crowded scene is more run-to-run sensitive than approach detection**,
which is itself a legitimate, useful finding for tuning `min_crossing_px` and
`approach_px` margins against real crowd density — not a defect to paper over.

## Honest limitations of this evaluation

1. **n=3 real clips is a smoke test, not a validation.** No night, fog,
   vehicle-only, or true idle-hour footage yet (Gate 2).
2. **Two of three clips are ~4.6-4.8s.** Tracker gating
   (`min_track_age_frames=8` at 6fps analytics ≈ 1.3s warm-up) leaves little
   margin in a clip that short; a longer real clip would be a fairer test.
3. **One hand-labelled event per clip, in scenes with many real people.**
   Every additional real pedestrian who also happens to cross the same line
   scores as a "false positive" against a label that only names one event.
   The false-alerts-per-idle-hour metric (0.00, from the negative control) is
   the more trustworthy number here, per P3.
4. **Detector inference order is not proven bit-deterministic** across
   separate CoreML sessions on this hardware in dense-crowd frames. Worth a
   dedicated regression test; not chased down further in this pass.

## What this session actually closed

- **Real, licensed, non-synthetic footage runs through the full pipeline** —
  detect → track → geometry → rules → debounce, with genuine person
  detections (10-18 people/frame) and genuine multi-second tracked
  trajectories, for the first time in this project.
- **Found and fixed a real bug**: `scripts/evaluate.py`'s zone loader never
  denormalised polygon coordinates against the clip's actual pixel dimensions,
  silently treating a 0..1-normalised zone as a single-pixel-wide box. This
  would have produced meaningless (uniformly near-zero) results for anyone
  running `make eval` with normally-authored zone files. Fixed in
  `load_zone_specs` / `build_zones`.
- **A genuine, reproducible negative result**: zero false alerts on a quiet
  real region over 13.9 real seconds.
